# 云计算课程设计：两人协作与上传规则

> 适用项目：cloud-course-design  
> 目的：规范两人协作流程，避免代码互相覆盖、截图丢失、报告材料混乱。

---

## 1. 仓库目录规则

项目统一使用以下目录结构：

```text
cloud-course-design/
├── backend/                 # Flask 后端代码
├── frontend/                # Nginx 前端页面与配置
├── k8s/                     # Kubernetes YAML 文件
├── docs/                    # 报告、说明文档、协作规则
│   └── screenshots/         # 实验截图
├── docker-compose.yml       # 本地联调配置
├── .gitignore               # Git 忽略规则
└── README.md                # 项目说明
```

所有实验截图统一放入：

```text
docs/screenshots/
```

不要把截图散放在根目录，也不要放在 backend 或 frontend 代码目录中。

---

## 2. 截图命名规则

截图文件名必须体现任务编号、内容和顺序，建议使用中文或英文均可，但必须清晰。

推荐命名：

```text
任务1-01-docker-compose启动成功.png
任务1-02-后端api返回status-ok.png
任务1-03-前端调用后端成功.png
任务1-04-后端日志收到请求.png
任务1-05-本地镜像构建结果.png
任务1-06-SWR镜像列表.png
任务2-01-CCE节点Ready.png
任务3-01-Pod运行状态.png
任务3-02-Service公网IP.png
任务3-03-api-ping访问成功.png
```

命名规则：

```text
任务编号-顺序号-截图内容.png
```

禁止使用以下模糊名称：

```text
截图1.png
新建图片.png
微信图片.png
QQ截图.png
屏幕截图.png
```

## 3. 分工规则

建议两人按模块分工：

| 成员 | 主要负责内容 |
|---|---|
| 成员 A | Docker、本地联调、SWR、CCE、K8s YAML |
| 成员 B | 实验截图整理、报告撰写、Spark/MPI、结果分析 |

如果某一方修改了对方负责的内容，必须先在微信/QQ/课堂群中说明，避免重复修改。

---

## 4. Git 提交流程

每次修改前先同步远程仓库：

```bash
git pull origin main
```

修改完成后查看状态：

```bash
git status
```

添加文件：

```bash
git add .
```

提交时必须写清楚本次修改内容：

```bash
git commit -m "docs: add task1 screenshots"
```

推送到 GitHub：

```bash
git push origin main
```

---

## 5. Commit 信息规范

推荐格式：

```text
类型: 修改内容
```

常用类型：

| 类型 | 含义 | 示例 |
|---|---|---|
| init | 初始化项目 | init: create project structure |
| feat | 新功能 | feat: add flask api |
| fix | 修复问题 | fix: update nginx config |
| docs | 文档或截图 | docs: add task1 screenshots |
| k8s | Kubernetes 配置 | k8s: add backend deployment yaml |
| report | 报告内容 | report: add task1 analysis |

不要使用无意义提交信息：

```text
update
111
修改
随便改一下
```

---

## 6. 防止代码被改乱的规则

1. 每次写代码前必须先执行：

```bash
git pull origin main
```

2. 不要同时修改同一个文件，尤其是：

```text
docker-compose.yml
backend/app.py
frontend/nginx.conf
k8s/*.yaml
```

3. 修改关键配置前，先复制备份一份，例如：

```text
backend-deployment.yaml.bak
```

4. 不要把本地密钥、华为云 AK/SK、SWR 登录密码、KubeConfig 上传到 GitHub。

5. 如果出现冲突，不要乱删代码，先截图发给组员或老师确认。

---

## 7. 敏感信息禁止上传

禁止上传以下内容：

```text
华为云 AK/SK
SWR 登录密钥
KubeConfig 文件
Redis 真实密码
Secret 明文文件
个人身份证、手机号截图
```

Kubernetes Secret 文件如果必须提交，只能提交模板，例如：

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: redis-secret
type: Opaque
data:
  password: <BASE64_PASSWORD>
```

---

## 8. 截图上传流程

本地截图统一复制到项目目录：

```text
docs/screenshots/
```

然后执行：

```bash
git add docs/screenshots/
git commit -m "docs: add experiment screenshots"
git push origin main
```

## 9. 报告引用截图规则

报告中图片按任务编号引用：

```text
图 1-1 Docker Compose 启动成功
图 1-2 后端 API 返回 status=ok
图 1-3 前端页面调用后端成功
图 1-4 后端日志收到 /api/ping 请求
图 1-5 本地 Docker 镜像构建结果
```

每张图下方必须写 1 句说明，说明该图证明了什么。

## 10. 最终提交前检查清单

提交前检查：

- [ ] GitHub 仓库可以正常打开
- [ ] backend、frontend、k8s 目录存在
- [ ] docker-compose.yml 存在
- [ ] docs/screenshots 中截图命名规范
- [ ] 报告中的截图编号和 GitHub 截图文件对应
- [ ] 没有上传 AK/SK、KubeConfig、真实密码
- [ ] README 或报告中写明两人分工
- [ ] 最终代码能通过 docker compose up --build 运行

---

## 11. 推荐两人协作方式

为了避免 main 分支混乱，推荐：

- 一个人负责最终合并和提交 main；
- 另一个人把截图、报告文字、YAML 修改发给负责人；
- 或者每个人使用自己的分支，确认无误后再合并。

分支示例：

```bash
git checkout -b member-a-k8s
git checkout -b member-b-report
```

合并前先确认项目可以运行。
